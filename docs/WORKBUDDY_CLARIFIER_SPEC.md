## 0. 一句话结论

工作台只做**确定性执行 + 证据输出**（已有能力，一行不放松）；WorkBuddy 作为**对话层**承担「理解 → 追问 → 确认 → 解释」，但**永不直接产出 plan、永不改引擎**。
M4 用户机上，WorkBuddy 是唯一入口：能读、能跑、能问、能提变更单；**不能改口径、不能改 golden、不能绕过复核**。
**不为对话层新增后端接口**——现有 `recognize` / `run_plan` / `validate_rows` / 结果表已足够（探针实证）。

## 1. 分层与边界（铁律）

| 层 | 内容 | 谁改 | 变更方式 |
|---|---|---|---|
| L0 数据 | `appdata/market/vipdoc`（通达信标准日线） | 每日管线 | 增量更新，幂等 |
| L1 引擎 | `recognizer.py` / `executor.py` / `validate_rows` / Skill 判定函数 / `golden/**` | **仅开发机** | 版本化打包下发；口径变更需 kk 裁定 |
| L2 编排 | workbench HTTP API（`/api/plan/*` 等） | 仅开发机 | 随包 |
| L3 对话 | **WorkBuddy + 本规格定义的两个 Skill** | kk / M4 用户 | 只产生「文本改写」与「诊断问答」 |

硬约束：
1. L3 **不得**直接写 plan JSON。plan 的唯一产生者是 `recognizer`，唯一校验者是 `recognizer.recognize` 的 READY 状态。
2. L3 **不得**修改 L1 任何文件；口径变更只能变成「变更请求单」回传开发机。
3. 模型说“能跑”不算数——**必须由 `/api/plan/recognize` 返回 0 problems 才算数**（fail-closed）。
4. 诊断结论的分类码与数字由代码判定；模型只允许做措辞润色，不得改写结论、不得补数字。

## 2. 回测前：澄清链路（clarifier）

### 2.1 链路（kk 口径：**只复用现有 recognise，不造第二套流程**）

```
用户输入规则（含截图 OCR）
   └─► 现有 /api/plan/recognize          ← 唯一权威，fail-closed
         ├─ 能执行（0 problems，无歧义）──► 正常确认 ──► 执行
         └─ 存在歧义 / 不可解析
               └─► WorkBuddy 按【当前这条歧义】动态生成：
                     ○ 选项 A   ○ 选项 B   ○ 自定义
                        └─► 用户选择
                              └─► 形成完整规则
                                    └─► 仍然走原 /api/plan/recognize（闭环，不旁路）
```

要点：
- 歧义选项**由发生歧义的那一条动态生成**（universe 未指明就只问 universe；措辞不可解析就给 1~2 个改写候选），**不做固定问卷**。
- 改写稿必须回灌原 recognize；**不 READY 就不算数**（模型不得自称“已支持”）。
- 现有已 Golden 验证的能力（多规则切分、歧义 resolve、D 记法变量间隔链翻译、符号约定行剥离）**一律复用**，不重写。

### 2.2 模型在链路中的权限（唯一合法动作）

- **合法**：把用户原文改写成识别器可解析的表述；解释为什么原表述不可解析；给出最多 2 个改写候选。
- **非法**：直接输出/编辑 plan JSON；宣称“已支持”；把不支持的片段静默删除后提交；改动 universe 等业务口径而不提示用户。
- 每份改写稿必须附：**改了什么 / 为什么改 / 语义是否等价的说明**，并标注「需用户确认」。
- 已知改写模板（识别器已在 `problems.reason` 中返回，模型可直接引用）：
  - D 记法双变量日 + 变量间隔 → 链式 `T_0-T_1间隔N1∈[a,b]，T_1-T_2间隔N2∈[c,d]，N1、N2自由组合`
  - 区间无涨停 = `T_0与T_1间无涨停`；仅三日涨停 = `仅T_0、T_1、T_2三日涨停`；前视无涨停 = `T_0前5日无涨停`
  - 双高 = `T_x的成交额和股价均是近20日最高`；输出间隔值 = `T_0与T_1间隔N1`
  - 「符号约定 / 说明 / 备注 / 注：」等说明行由 `_drop_notation_lines` 自动剥离（不含业务关键词时）
  - 同上多个条件用**逗号**连，不要用分号

### 2.3 plan 确认卡片（给用户逐项确认，替代“直接出结果”）

| 字段 | 来源 | 示例 |
|---|---|---|
| 宇宙 universe | `strategy_plan.universe` | 10cm（沪/深主板）/ 20cm（创业板、科创板）/ both |
| 锚点 | `chain.anchors` | T_0、T_1、T_2（或 D-y / D-x / D-0） |
| 各锚点条件 | `chain.anchor_conds` | 涨停 / 成交额近 20 日最大 / 股价近 20 日最高 / 前 5 日无涨停 |
| 间隔区间 | `chain.gaps` / `span_gaps` | N1∈[1,5]、N2∈[1,5]，自由组合；跨间隔和约束 |
| 区间约束 | `gap_conds` | T_0~T_1、T_1~T_2 内均无涨停；仅三日涨停 |
| 输出列 | `strategy_plan.outputs` | D-0 日期、N1/N2、各锚点振幅、区间涨幅/振幅、D+1~D+8 走势 |
| 数据截止日 | `/api/data/latest` | 2026-09-22 |
| 标的数（预计） | 由 universe 决定 | 10cm 主板 ≈3483 只（当前口径，未含 30 开头 10cm 阶段） |

### 2.4 接口（建议 A，**暂不实施**）

`GET /api/plan/capabilities` —— 从 `recognizer` 的模式表导出「已支持表达 / 改写模板 / 明确不支持（如 C6 前向窗口待排期）」。
**暂缓理由**：识别器已在 `problems.reason` 里返回改写模板，WorkBuddy 侧直接消费即可，无需新增接口。

## 3. 回测后：质疑诊断（**已证伪为不必要，保留作废案**）

场景示例：「在 121 规则下，芯源微(20200117) 这个数据是不是遗漏了？」

> **探针结论（2026-09-22）**：这一整节**不需要实现**。
> `artifacts/verification/capability_probe/REPORT.md` 证明：用现有 `store.get_rule` + `run_plan`（收窄宇宙）+ `compute_limit_flags` / `rolling_max20` / 结果表比对，
> 七项能力（定位股与日、用正式规则、用 Skill 判定、逐条件检查、取实际数值、指出不满足的条件、识别不一致）**全部可达**，
> 且已在 18 个在库模型上实测 `inconsistency=NO`。**下方码表与接口仅作废案存档，不实施。**

### 3.1 接口（废案，不实施）

`POST /api/diagnose/row`，入参：`{stem | rule_text, code, date}`（日期可给 ±1 交易日容错）。
出参：`{verdict_code, checks[], evidence{}, explanation_template, data_date}`。

### 3.2 判定顺序（确定性，复用 executor 既有判定函数）

按序短路，命中即返回，全部证据随行输出：

| 码 | 含义 | 依据（复用） |
|---|---|---|
| `NOT_IN_POOL` | 该股不在本条规则的宇宙内（板块/前缀） | `_collect_stock_files(universe)` |
| `DATA_MISSING` | 该日无数据 / 停牌 / 水位落后 | vipdoc `.day` 读盘 + 交易日历 |
| `NO_LIMIT_DAY_EXCLUDED` | 无涨跌幅限制日被严格 `==` 口径剔除 | `compute_limit_flags`（Skill 权威实现，严格相等，非 `>=`） |
| `ANCHOR_FAIL` | 某锚点条件不满足 | `_chain_anchor_ok` / `_mask_for_days` |
| `GAP_FAIL` / `SPAN_FAIL` | 相邻间隔越界 / 跨间隔和约束不满足 | `_run_chain` 间隔组合过滤 |
| `RANGE_FAIL` | 区间内出现额外涨停 | `gap_conds` |
| `PREV_NO_LIMIT_FAIL` | 更早一侧紧邻 5 日出现涨停 | `prev_no_limit` |
| `FORWARD_INSUFFICIENT` | 前向窗口不足（照发 N/A，C6 待排期） | `generate_t_fields` / `chain_walk` |
| `ROW_INVALID` | 复核剔除 | `validate_rows` |
| `SHOULD_HAVE_HIT` | 应命中却未出 → **判定器自身缺陷信号**，最高优先级，需回传开发机 | 全链重算与结果表比对 |

### 3.3 evidence 内容（可复核、可回传）

原始 OHLC、原始成交额、前收、**涨停价计算过程**（昨收 × 1.1 / 1.2，四舍五入到分）、近 20 日成交额排名、同期同股其他命中行、该日是否停牌/缺口、数据截止日。
人话模板由结论码拼装。**注意**：探针已证伪一处想当然的解释——芯源微 20200117 **不是**「上市前 5 日无涨跌幅限制」被剔除（该窗口是 20191216~20191220，20200117 是第 24 个交易日），真实原因是当天**根本没封板**（收 102.80 / 涨停价 112.80）且 688 不在 10cm 池内。
→ 教训：**解释必须由数据推出，不能由模板套出**。

## 4. M4 用户侧治理（WorkBuddy 封装）

### 4.1 允许 / 禁止

| 允许 | 禁止 |
|---|---|
| 启动与健康检查、每日增量状态查询 | 修改 `recognizer.py` / `executor.py` / `skill/**` / `golden/**` |
| 提交规则、走澄清链路、跑回测、查看/导出结果 | 修改口径、放宽比较器、跳过 `validate_rows` 复核 |
| 对结果质疑并取诊断证据 | 用模型结论替代识别器判定 |
| 生成「变更请求单」并回传 | 在用户机直接改代码后继续使用 |

### 4.2 硬约束落地（三道门）

1. **哈希自检门**：随包生成 `MANIFEST.sha256`（覆盖 `recognizer.py` / `executor.py` / `skill/**` / `golden/**` 清单）。Skill 每次会话开工前自检，任何不符 → 拒绝执行并提示「引擎完整性异常，请联系分发方」。
2. **写操作黑名单**：Skill 只调用 L2 的 HTTP API；禁止对工作区源码目录执行写/改操作。
3. **变更请求门**：口径类改动一律生成 `artifacts/change_requests/CR-YYYYMMDD-<slug>.json`（含用户原文、意图、期望行为、证据、复现步骤），通过 agent-mail 回传 kk；SKILL 明确「本机不实装」。

### 4.3 三档响应策略

- **改表述**：用户自己按改写稿调整原文 → 立即可用（最多 1 轮）。
- **登记**：属能力缺口 / 口径问题 → 出变更请求单，回传开发机裁定。
- **拒绝**：越权（改源码、改口径、绕复核）→ 明确拒绝并说明原因。
